# KaizenHub — правила проекта

Веб-приложение «Конвейер проектов» (один файл `index.html`, без сборки). Данные и вход — Supabase,
хостинг и серверная функция — Vercel, код и история — GitHub. Пользователь не программист: объясняй
простыми словами, действуй шагами, перед необратимыми действиями спрашивай.

## Структура
- `index.html` — всё приложение (интерфейс и логика). Правим точечно, не переписываем целиком.
- `claude-shim.js` — «переходник»: приложение вызывает `window.claude.use('user' | 'db' | 'sample')`,
  а файл превращает это в запросы к Supabase и к `/api/sample`. Экран входа тоже здесь.
- `config.js` — публичный адрес Supabase и publishable-ключ (их можно коммитить).
- `api/sample.js` — серверная функция Vercel: прокси к Claude (скриншоты, AI-резюме). Проверяет вход и лимиты.
- `supabase/migrations/` — изменения базы. Таблица `docs` хранит «документы» по путям `sp/…`, `inv/…`, `data/users/<id>/…`.
- `tests/` — автотесты (`cd tests && npm install && npm test`). Права и миграции: `npm run test:db` (нужен локальный Postgres: `brew install postgresql@16`).

## Железные правила
1. **Секреты не коммитим.** Нельзя в код, чат и логи: `sb_secret_…`, `service_role`, пароль базы,
   `ANTHROPIC_API_KEY`, токены. Они лежат в Vercel (Environment Variables) и GitHub (Secrets). `.env` в `.gitignore`.
2. **Миграции только вперёд.** Применённый файл в `supabase/migrations/` не правим и не удаляем. Любое изменение базы —
   новый файл `YYYYMMDDHHMMSS_название.sql`. Опасные операции (`drop`, `delete`, `truncate`) — только после явного «да» пользователя.
3. **Права доступа (RLS и функции `doc_set`, `doc_update`, `doc_delete`) меняем осторожно:** после правки пишем/прогоняем
   тест на роли «владелец / участник / посторонний / гость по ссылке». Запись в `docs` идёт только через функции, не напрямую.
4. **Перед пушем** запускаем `tests`. Красные тесты не пушим.
5. **Работаем в ветке**, в `main` — только после проверки на preview-ссылке Vercel. Коммиты короткие, по-русски, по делу.
6. Не добавляем сторонние библиотеки и CDN без необходимости. Скрипты подключаем с точной версией.

## Как выкатывается
- Пуш в ветку → Vercel делает preview-ссылку. Пуш/мерж в `main` → Vercel обновляет боевой сайт.
- Изменения базы: GitHub Actions (`.github/workflows/supabase-deploy.yml`, добавим отдельным шагом) выполняет `supabase db push` при пуше в `main`.
- ВАЖНО: первая миграция `20261020000000_init.sql` уже применена вручную в SQL Editor. Перед включением workflow один раз
  выполнить `supabase migration repair --status applied 20261020000000`, иначе `db push` попытается создать таблицы заново и упадёт.

## Переменные окружения Vercel
`ANTHROPIC_API_KEY`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` (необязательно: `ANTHROPIC_MODEL`, `ANTHROPIC_MODEL_FAST`).

## Известные особенности
- Вход: Google (кнопка на экране входа) или почта и пароль. Новичок, пришедший через Google по ссылке-приглашению,
  получает роль исполнителя (`user_metadata.role = guest`) в `claude-shim.js` → `markInvitedGuest`.
- Исполнитель во вкладке «Мои проекты» меняет статус этапа и отмечает подэтапы без чек-листа; правки уходят владельцу через `sp/<проект>`.
- Почта и пароль: «Confirm email» в Supabase выключен на время теста. Перед запуском для людей:
  подключить свой почтовый сервис (custom SMTP) и снова включить подтверждение почты. Встроенная почта Supabase шлёт 2 письма в час.
- Удаления Supabase Realtime не присылает: `claude-shim.js` раз в 20 секунд сверяется с базой.
- Лимит запросов к Claude (20 за 10 минут на человека) считается в памяти функции; для жёсткого лимита нужна таблица в базе.
- Команда по ссылке: «Команда → Пригласить» даёт одноразовую ссылку (`inv/<код>`, kind `team`). Вошедший пишет себя в `team/<владелец>/members/<id>`,
  владелец привязывает его к сотруднику (`account_id`) и сам открывает проекты, где тот назначен (`share.members` с `auto:true`).
- Профиль (`public.profiles`): имя, фото из Google, должность (`job_title`), контакт. Человек правит только свой.
- Шаблон процесса: этапы → подэтапы → карточка подэтапа (описание, регламент, видео, чек-лист) в «Настройки → Шаблоны».
  Карточки хранятся в `db.cardTpls["<шаблон>|<подэтап>"]`; новый проект получает их сразу (`copyCards`),
  идущие — сразу при сохранении шаблона (`applyTplToProjects` + `syncCardToProjects`). Галочка «Сохранить как шаблон» в карточке
  проекта тоже обновляет эту карточку во всех активных проектах процесса. Отметки чек-листа сохраняются, сданные этапы и
  выполненные чек-листы не открываются заново, пустая карточка шаблоном не становится.
- Блоки карточки (`t.blocks`: текст, ссылка, видео, файл) добавляет руководство в режиме редактирования и в шаблоне (`c.b`).
  Файлы — Supabase Storage, корзина `kz-files` (миграция `20261022000000_card_files.sql`): `<uid>/p/<проект>/…` и `<uid>/t/<шаблон>/…`;
  при сохранении карточки шаблоном файлы копируются в папку шаблона (`promoteTplFiles`).
- Категории проектов: `db.categories` ([{id,name,color}], «Настройки → Категории»), у проекта `category_id`.
  Главная по умолчанию группирует по категориям (`ui.group = 'auto'` → `groupMode()`), «Без категории» — последней.
- Пространства («Настройки → Пространства»): основное — `data/users/<id>`, другие — `data/users/<id>/spaces/list/<sp>/items`,
  список — `data/users/<id>/spaces/list`. Текущее помнит браузер (`kz-space`), своё хранилище `agency-pipeline-demo-v2-<sp>`.
- Открытый раздел помнит вкладка (`sessionStorage` `kz-view`) — не через адрес: адрес нужен входу через Google.
- Порядок этапов: номер = место в списке; один раз на проект восстанавливается по шаблону (`repairStageOrder`, флаг `orderChecked`).
- Сроки этапов: «Настройки → Дедлайны» — дней на этап (`db.prefs.stageDays`, по умолчанию 2) или дни из шаблона (`useTplDays`).
  Финальный дедлайн (`p.deadline`) задаёт пользователь; «Уместить в дедлайн» (`fitToDeadline`) сжимает оставшиеся этапы.
  Поля дат в карточке проекта сохраняются при выходе из поля или Enter (иначе ввод с клавиатуры сбивается).
- Сроки пересчитываются «вживую» (`replan` в `save()` и раз в час): незавершённые этапы идут от фактического конца предыдущего,
  не раньше сегодня; длительности этапов и дедлайн клиента (`p.deadline`) не меняются.
- Данные из версии на claude.ai переносятся вручную: облачко → «Импорт данных из файла» (`mergeSnapshot`, файл `data/kaizenhub-snapshot.json`,
  папка `data/` в git не попадает — там личные данные).
- Облако и несколько вкладок/устройств: при чужих изменениях вкладка с несохранёнными правками сливает данные (`mergeRemote`):
  свои изменённые проекты/задачи/отчёты и поля настроек оставляет, остальное берёт из облака. База сверки — `cloud.hashes`
  и `cloud.baseMeta`, хранятся в `localStorage` `<KEY>-sync`, чтобы и после перезахода не затирать чужие изменения.
- Подэтап, добавленный в одном проекте и сохранённый «как шаблон карточки», попадает в шаблон и во все идущие проекты.
  Обновление по шаблону не удаляет подэтапы, добавленные только в проекте (`mergeSubs(..., keepExtra)`).
- Вход: вкладки «Руководитель» / «Исполнитель» (`claude-shim.js`, выбор переживает Google через `sessionStorage` `kz-who`).
  Руководителем входит только аккаунт с доступом: есть своё пространство (`data/users/<id>/meta`) или `user_metadata.role = 'lead'`.
  Иначе — выход и подсказка войти исполнителем. Это проверка интерфейса; данные и так разделены правами базы по аккаунтам.
  Новичок на вкладке «Исполнитель» получает `role = guest`.
- Общая ссылка для исполнителей («Команда → Ссылка для исполнителей»): многоразовая `inv/<код>` (kind `team`, `common:true`),
  код в `db.prefs.teamLink`. Вошедшие добавляются в «Команду» сами (`addCommonJoins`) или привязываются к сотруднику с той же почтой.
- Выбор проектов на главной («Выбрать»): галочки у строк (`paintSelect`, клик в режиме выбора перехватывается),
  панель внизу — «Выбрать все», «В архив», «Удалить» (`deleteProjects` удаляет и карточки/отчёты проектов).
- Приглашения: приложение писем не отправляет. В окне ссылки — кнопки «Почта» (mailto на адрес сотрудника), Telegram, WhatsApp
  с готовым текстом (`sendLinkHtml`). В списках выбора ответственного/PM помечено «(не вошёл)».
- Руководитель (миграция `20261023000000_team_managers.sql`): «Команда → Пригласить» с галочкой «Доступ руководителя» →
  одноразовая `inv/<код>` с `role:'lead'`. Вошедший пишет себя в `team/<владелец>/managers/<id>` и `data/users/<id>/links/lead/<владелец>`,
  получает `user_metadata.role = 'lead'` (claude-shim.js), браузер запоминает `kz-org`; дальше `cloud.col = data/users/<владелец>`,
  «Вы» = его запись в команде (`ME`, `adoptOrgMe`), общие проекты и ссылки — от имени владельца (`OWNER()`).
  Руководитель не приглашает новых руководителей; отдельные пространства и личные ссылки владельца ему недоступны.
  Убрать — удалить человека из «Команды» (снимается `team/<владелец>/managers/<id>`).
- Руководитель области (миграция `20261110000000_area_leads.sql`): «Пригласить» с галочкой, нажатое в отдельном пространстве,
  даёт доступ только к пространствам его области — `inv/<код>` с `role:'arealead', area`. Вошедший пишет себя в
  `team/<владелец>/areas/<область>/<id>` и `data/users/<id>/links/area/<владелец>.<область>`; браузер запоминает
  `kz-org = '<владелец>:<пространство>'` (`ORGK`, `ORG`, `ORGSP`), `cloud.col = spacePath(владелец, пространство)`.
  База пускает только в пространства, чья запись `spaces/list/<пр>.area` = эта область (`markAreaSpaces` вписывает `.area` явно);
  основное пространство, другие области, команда, общие проекты и ссылки ему недоступны (`scheduleShared`, `watchTeam` выключены).
  Пространства области — в `spaces.orgs` (`areaOrgs`). Галочка в основном пространстве — прежний общий руководитель.
- Задачи в двух видах (`renderMyDay(mode)`): «Производство → Мои задачи» (`exec` → `renderTodo`: простой список с галочкой
  «выполнено» — у внутренней статус «Готово», у карточки весь чек-лист, у подэтапа отметка; как у исполнителя, с «Смотреть как: сотрудник»)
  и вкладка главного меню «Поручения» (`ui.view = 'assign'`, `admin`: постановка, сроки подзадач, внутренние задачи по людям,
  проекты по умолчанию свёрнуты — `ui.dayFold`, «Развернуть все»). У исполнителя — отдельная вкладка
  «Задачи» (`ui.view = 'mytasks'`, на телефоне — в нижнем меню).
- Лента задач (`renderMyDay`): проектные подзадачи только текущего этапа активных проектов
  (`dayProjectItems`, ответственный = `whoId`) + внутренние задачи. Подфильтры «Все / 💼 Проектные / 🏢 Внутренние»,
  у руководителя — выбор исполнителя и «+ Внутренняя задача». Исполнитель видит то же в «Мои проекты → Задачи» (`renderMine`).
- Внутренние задачи — документы `it/<id>` { ownerId, memberIds:[владелец, аккаунт исполнителя], json } (миграция
  `20261024000000_internal_tasks.sql`). Ставят/удаляют владелец и руководители, исполнитель меняет статус. Удаление: сначала
  пометка `deleted` (её получают все сразу), потом удаление. Без входа в аккаунт — `db.itasks` локально.
- В общий проект (`sp/<id>.json._team`) пишется соответствие «сотрудник команды → аккаунт»: так исполнитель знает свои подзадачи.
- Задачи по проектам — блоками на проект (сворачиваются, `ui.dayFold`). Срок подзадачи ставит руководитель в карточке:
  `t.due_date` у карточки, `x.due_date` у подэтапа без карточки (иначе — срок этапа).
- Уведомления: колокольчик есть и у исполнителя — «Новые задачи» (ещё не видел, `<KEY>-seen`), «Просрочено», «На сегодня»
  (`myAlerts`), у руководства ещё горящие этапы. Уведомления браузера — по кнопке в колокольчике, пока сайт открыт (`pushNotify`).
- Синхронизация шаблона с проектами (`syncAllTemplates` → `syncProjectWithTemplate`, при загрузке и сохранении шаблона):
  этап проекта помнит этап шаблона `s.tsid`, подэтап — `x.tsub` (старые связываются по названию, затем по месту в цепочке).
  Переименование переносится, новые этапы/подэтапы встают на место (если проект не прошёл его), удалённые из шаблона убираются,
  если в них нет работы (иначе остаются своими, `custom`). Пустые не начатые этапы вне шаблона убираются. Этап шаблона, удалённый
  в проекте вручную, не возвращается (`p.tplSkip`). Этапы, добавленные в проекте (`addStage`), — `custom`. Завершённые проекты не трогаем.
- Абонентское ведение: у проекта `p.is_maintenance` (галочка при создании и в карточке проекта). В конце цепочки — системный
  этап `s.system = 'maint'` «Ведение / Поддержка» (`syncMaint` в `syncState`): «не начат», пока воронка не пройдена, потом бессрочно
  «в работе» — проект не закрывается. Регулярные задачи — `s.rtasks` этапа ведения { title, assignee_id, frequency weekly|biweekly|monthly,
  status, due_date, last_done, done_count }; галочка «выполнено» переносит срок на следующий цикл (`completeRtask`, `nextCycle`).
  Видны: карточка проекта, колонка «Ведение» на канбане, «Производство → По проекту», у исполнителя; в задачах — отдельной вкладкой
  «Ведение» («Мои задачи»/«Задачи» исполнителя: `ui.todoTab`, «Поручения»: `dayTab = 'm'` → `renderAssignMaint`).
  Статус ведения — свой ключ `maint` и фиолетовый цвет `--m`, фильтр «На ведении».
  Хранятся внутри проекта — отдельной таблицы и миграции не нужно, права те же, что у проекта.
- Шаблон сообщения подэтапа: в редактировании (карточка проекта и карточка шаблона) — галочка «Шаблон сообщения» и поле текста
  (`msgEditor`; хранится как блок `type:'msg'`, расходится по проектам вместе с карточкой). Подстановки {клиент} {проект} {этап} {pm}
  {подэтап} (`fillMsg`). У подэтапа справа — иконка (`msgIcon`), в окне подэтапа — в шапке; нажатие открывает окошко с готовым
  текстом и «Копировать» (`openMsgPick`, `copyText`). Клик по иконке не открывает подэтап (перехват в capture).
- Меню-панель в стиле Arc (`renderSide`): кнопка слева от логотипа или мышь к левому краю; разделы, текущее пространство, пространства
  цветными кружками («+» — новое). Можно закрепить (`kz-side-pin`, `body.side-pinned`: панель сдвигает страницу, верхние вкладки скрыты).
  Цвет пространства: `spaces/list/<id>.color`, у основного — `data/users/<id>/spaces/main.color`; текущий окрашивает `--brand`/`--space`
  (`applySpaceColor`, кэш `kz-space-colors`). У пространства есть иконка (`icon`, набор `SP_ICONS`); в панели — только кружки с иконками
  (название — в подсказке и наверху панели). Иконка и цвет выбираются в «Настройки → Пространства».
- Фильтры статусов — с иконками статусов (`chipIco`, те же, что в плашках `STATUS_ICO`), а не цветными точками.
  Светлая тема — насыщенные цвета статусов (`--g --y --r --b --m`), как в тёмной.
- Светлая тема: фон страницы чисто белый, фильтры (статусы, поиск, списки, переключатели) — светло-серые `--fbg`
  (правила через `:where`, чтобы выбранный статус оставался цветным).
- Шапка: только «Новый проект» и колокольчик (квадрат в рост кнопки). Профиль, тема и состояние сохранения — внизу панели
  (`sideFoot`; кнопки в шапке `#cloudBtn #themeBtn #meBtn` скрыты, но остались — на них завязаны обработчики).
- Фото проекта `p.image`: квадрат со скруглением (`projAva`), загружается при создании проекта и в карточке проекта (клик по квадрату), обрезается по центру
  до 160×160 и сжимается в JPEG до ~60 КБ (`squareImage`) — хранится в проекте, видно и исполнителям. Нет фото — буквы названия
  на градиенте с постоянным цветом проекта (`pHue`). Показ: список/матрица, канбан, производство, поручения, телефон, карточка.

## Фильтры (строка над списком)
- Сортировка только: по срочности / по дедлайну / по названию. Группировка: по категориям / по процессу / по PM / без групп.
  Убраны «по финишу», «по приоритету», группировка «по клиенту» и «по приоритету» — старые значения из ui сбрасываются в renderFilters.
- У каждого контрола своя иконка (`.sel-ico` для select, svg в `#fToggle`, `#selToggle`, `#density`).
- На ширине >1100px строка не переносится; при закреплённой панели (≤1440px) подписи «Список/Этапы/Выбрать» прячутся, остаются иконки.

## Телефон: карточки, Производство, меню

## Загрузка файлов (важно)
- Лимит файла — 50 МБ (миграция `20261029120000_files_50mb.sql`, `MAX_FILE` в shim). Supabase Storage принимает в пути только латиницу, цифры и `/ ! - . * ' ( ) & $ @ = ; : + , ?` и пробел — на кириллицу отвечает «Invalid key». `safeFileName` переводит русские и казахские буквы в латиницу и оставляет `[A-Za-z0-9._-]`; в карточке показывается исходное имя (`name`). Тестовая заглушка `tests/fake-supabase.js` проверяет путь тем же правилом.
- «Сдача работы»: `uploadMats(t, files)` — несколько файлов сразу и перетаскивание в блок (`[data-matdrop]`). Ошибки — `uploadErr`.
- Приёмка: руководитель/PM нажимает «Принять» у материала (`m.ok`, `okBy`, `okAt`); исполнитель видит «Принято» или «на проверке». В запросе на переход (`gateBox`) — список сданных материалов этапа (`gateMats`).
- Кто принимает: `reviewProjects()` — свои проекты (и кабинет владельца у руководителя команды) + открытые по ссылке с ролью «Руководитель». `matsToReview()` — непринятые материалы (свои не считаются). «Принять» видят все с `canEditProject(p)`; руководитель по ссылке в запросе на переход видит «Одобрить / Вернуть».
- Уведомления: колокольчик — «Материалы на проверку» и «Запросы на переход» (и у руководителя по ссылке); на устройство (`pushNotify`) — «Новые материалы на проверку» и «Запрос на переход», каждое один раз (`NSENT_KEY`: `mat:<id>`, `gate:<stage>:<at>`).
- `ensureSharedTasks()` (в `save()` и при загрузке): в проектах, открытых исполнителям, у каждого подэтапа с карточкой в шаблоне сразу создаётся задача — иначе исполнитель видит только галочку «Отметьте, когда сделаете» (шаблонов карточек у него нет).

## Сдача этапа (основной путь исполнителя)
- Под каждым этапом у исполнителя блок «Сдать этап» (`stageSubmitBox`): поле ссылки, «Файлы» (несколько, перетаскивание), «Отправить» — без комментария; вставленная ссылка уходит при «Отправить». Данные — в этапе: `s.sub = { status:'draft'|'pending'|'rejected'|'accepted', items, note, by, byName, at, reason, decidedBy, decidedAt }`.
- Руководитель (все с `canEditProject`) видит под этапом сданное и «Принять этап» (→ `setStatus(p,s,'done')`, следующий этап в работе) или «Вернуть» с причиной. В колокольчике — «Сдача этапов» (`stageSubmissions()`), на устройство — «Сдача этапа».
- Исполнитель сам «Завершён» не ставит ни на каком этапе. Ссылок «Прикрепить материалы» у подэтапов на доске больше нет; старый запрос на переход (`s.req`) показывается, только если уже был отправлен.
- Раздел «Приёмка» (`ui.view = 'review'`, `renderReview`): вкладки «На проверке» (сданные этапы с «Принять этап / Вернуть», старые запросы на переход, непринятые материалы в карточках), «Принятые», «На доработке» (`reviewHistory`). Цифра на пункте меню — `paintReviewBadge`. Исполнителю раздел виден, только если ему открыли проект с ролью «Руководитель» (`guestViews()`).
- Синхронизация общего проекта пишет его целиком — правки двух людей затирали друг друга (сдача этапа терялась, если владелец в ту же секунду сохранял). `mergeStageFields` сливает `s.sub` и `s.req` по времени изменения (`u`, ставит `ssTouch`) в `onSharedProject` (и когда у владельца есть несохранённое) и в `rebuildExt`; более новое у себя — досылается. Принятие этапа переносит и статусы этапов. Тест на гонку — в `gate.test.js`.

## Синхронизация: устаревшие снимки
- В `claude-shim.js` счётчик своих записей `writeSeq` (растёт до и после каждого `set/update/delete`). Если за время загрузки снимка (`L.load()`) была своя запись, снимок мог прочитать базу до неё — его не отдаём приложению, а грузим заново. Иначе только что сохранённое на время откатывалось («подгружает старые данные»), а правка в этот момент могла записать старую версию поверх новой. Тест — в `shim.test.js` (медленная сеть `readDelay` в `fake-supabase.js`).
- Старое устройство не затирает облако: при открытии облако главнее. «Своими несохранёнными» считаются только документы из списка `KEY-dirty` (`markDirty()` в `scheduleCloud` — документы, отличающиеся от облака после сверки; очищается после успешной записи). Раньше своими считались все копии, отличавшиеся от прошлой сверки (в т.ч. пересчитанные при открытии `replanAll`), а при отсутствии `-sync` весь браузер записывался поверх облака по `savedAt`. Тест — `stale.test.js`.
- Кнопки в низу боковой панели (и в окне облака): «Сохранить» (`saveNow` — сразу записать) и «Синхронизировать» (`syncNow` — дописать свои правки и забрать всё из облака заново, облако главнее).
- Вкладка в фоне тоже сверяется с облаком (каждый третий опрос), при возврате на вкладку — сразу.
- Общий проект пишется целиком, поэтому старая копия у исполнителя откатывала статусы этапов у владельца. Теперь `stampStages()` (в `save()`) ставит отметку времени: этапу `s.su` — при смене статуса, дат факта или ответственного; галочке подэтапа `x.u` — при отметке. `mergeStageFields` берёт статус этапа и каждую галочку от того, у кого отметка новее; копия без отметок (старая версия приложения) не перебивает этап с отметкой. Полученные данные запоминаются `rememberStages`, чтобы не считаться своими правками. Тест — `stale.test.js`.
- Автозакрытие этапа (`autoCloseStages`, вызывается `queueAutoClose` после отметок: галочка подэтапа, пункт чек-листа, «Мои задачи», сохранение карточки). Все подэтапы текущего этапа выполнены → `setStatus(done)`, следующий в работе, дальше по цепочке. Этап с приёмкой (`needsAccept`: `s.gate` или подэтап с `files`): у исполнителя создаётся сдача `s.sub` со статусом `pending` → «Приёмка»/колокольчик, закрывает руководитель «Принять этап». Если последнюю отметку ставит руководитель — этап закрывается сразу (это приёмка). При загрузке и синхронизации шаблонов этапы сами не закрываются.
- Старт проекта — день, когда первый этап взяли в работу (`p.started_at`, ставит `markStarted` в `save()`; `p.start_date` становится этой датой). Новый проект сам не стартует (`createProject` не ставит этап «в работе», `ensureActive` ждёт начала работы). Пока работа не началась — «Не начат, план …» (`notStarted`, `startTxt`, `startCell`), а сроки этапов сдвигаются вместе с сегодняшним днём (`replan`). Первая отметка подэтапа запускает текущий этап и при плановом старте в будущем.
- Логотип убран из шапки (`.top .brand` виден только с названием пространства) — тихий значок `.side-brand` внизу боковой панели под профилем.
- Карточки подэтапов в общих проектах (`sp/<pid>/tasks/<id>`) пишутся целиком. `stampTasks()` (в `save()`) ставит `i.u` пункту чек-листа при отметке/снятии и `t.u` карточке при прочих правках; `onSharedTasks` больше не пропускает чужие изменения, когда у себя есть несохранённые (раньше их хэш запоминался, а своя запись затирала отметки исполнителя), а сливает `mergeTask`: поля — от более поздней правки карточки, каждая галочка — по более свежей отметке (`ckStamp`), материалы и их «Принято» не теряются; если результат отличается от облака — досылается. Своих карточек, которых ещё не было в облаке, не теряем. Тест — `stale.test.js`.
- Под этапом у исполнителя больше нет блока «Сдать этап»: материалы — только в карточках подэтапов. Этап с приёмкой уходит руководителю сам (все пункты отмечены), исполнитель видит «Этап на приёмке у руководителя»; если вернули — причина и «Отправить снова» (`ssSubmit`). У руководителя под этапом — «Принять этап» / «Вернуть».
- Статусы у руководителя: свой проект приходит и из своего облака (`data/users/<uid>/p_`, пишут все устройства руководителя), и из `sp/<pid>` (пишут исполнители). `cloudApply` больше не подменяет проекты и карточки целиком: `keepFreshStages(prevP, prevT)` сливает этапы (`mergeStageFields`) и карточки (`mergeTask`) с прежней копией и с последним полученным общим документом (`shared.remote`, `shared.rtasks`) — старая копия с телефона руководителя не откатывает статусы, выставленные исполнителем. Тест — `tests/leadview.test.js`.
- Приёмка материалов закрывает этап: подэтап считается выполненным, если руководитель принял все его материалы (`matsAccepted` в `subDone`); «Принять» у последнего материала ставит `x.done` и запускает `queueAutoClose`. Этап, где все сданные материалы приняты, закрывается без отдельного «Принять этап». Когда приходят отметки исполнителя (`onSharedProject`/`onSharedTasks`), у руководителя запускается `autoCloseStages(p, true)` (passive): этап без приёмки закрывается, этап с приёмкой уходит в «Приёмку» (`s.sub` pending) — даже если у исполнителя старая версия приложения. Тест — `leadview.test.js`.
- Приложение на iPhone (без App Store): `manifest.webmanifest`, иконки в `icons/` (тёмный квадрат с тремя точками, как `.sb-dots`), в `<head>` — `apple-touch-icon`, `apple-mobile-web-app-capable`, статус-бар `black-translucent` (отступы `safe-area-inset` уже есть). Ставится: Safari → «Поделиться» → «На экран „Домой“» — открывается на весь экран, без адресной строки.
- Приложение для iPhone на React Native (Expo): папка `mobile/` — WebView с https://kaizenhub-nu.vercel.app (`App.js`), bundle id `com.tsoyalax.kaizenhub`. Папки `ios/`/`android/` генерируются (`npx expo prebuild`), в git не попадают. Вход через Google: приложение перехватывает переход на `…supabase.co/auth/v1/authorize`, открывает его в системном окне входа iOS (`expo-web-browser` `openAuthSessionAsync`, Google его пускает, WebView — нет) с возвратом на `kaizenhub://auth` и отдаёт токены сайту в адресе (supabase-js `detectSessionInUrl`). Окно входа открывается через `app-auth.html` (ставит в sessionStorage `kz-app-auth` и идёт к Supabase); когда Google вернёт на сайт, ранний скрипт в `<head>` index.html видит отметку и токены в адресе и отправляет их в приложение `kaizenhub://auth…` — отдельный адрес возврата в настройках Supabase не нужен. Почта/телефон/Telegram/WhatsApp и чужие сайты открываются снаружи. Сборка для симулятора: `cd mobile/ios && LANG=en_US.UTF-8 pod install`, затем `xcodebuild -workspace KaizenHub.xcworkspace -scheme KaizenHub`.

## Тип пространства: Агентство / SMM / CRM, теги, выбор пространства
- Тип — `db.prefs.kind` ('smm' или нет) открытого пространства; дублируется в документе пространства (`spaces/list/<id>.kind`, у основного — `spaces/main.kind`, там же `name` основного). Меняется в «Настройки → Пространства» (`[data-spkind]`), выбирается при создании.
- SMM (`isSMM()`, подписи через `W('проект', 'видео')`): шаблон «SMM: видео» (`ensureSmmTemplate`, id `tsmm`), у видео без фото — иконка видео (`projAva`), группировка «По неделям» и блок «План / Факт» (`smmPanelHtml`) — по циклам из 4 недель от даты старта пачки: у видео `p.cycle` (дата старта) и `p.week` (1–4); план цикла — `db.prefs.smmCyclePlans[start]` (по умолчанию число видео; меняется кнопкой «Редактировать» вместе с датой старта — `moveCycle` сдвигает видео цикла), по неделям поровну (`splitPlan`: 45 → 12/11/11/11); факт — снятые/опубликованные по дате завершения этапа (`weekOfDate`). Одиночное видео попадает в цикл по дате публикации (`cycleFor`). Снято/опубликовано — по завершению этапов с названием «Съёмка» / «Опубликовано» (`stageDoneAt`, `RX_SHOT`, `RX_PUB`; нет этапа «Опубликовано» — последний этап).
- CRM «Блогеры» (`isCRM()`, `kind:'crm'`, подписи — третий аргумент `W(агентство, smm, crm)`): шаблон «CRM: оффер на запуск» (`ensureCrmTemplate`, id `tcrm`: Найден → Первый контакт → Переговоры → Встреча → Оффер отправлен → Условия согласованы → Договор подписан → Запуск). Главная в CRM — список блогеров (`density()` по умолчанию compact) со сводкой `crmSumHtml()` (цифры + чипы этапов, клик — фильтр); полная воронка — отдельный вид `density()==='funnel'` → `crmPanelHtml()`: воронка по `crmStats()` (reached — дошли до этапа, at — стоят на нём, won — все этапы пройдены, lost — в архиве не дойдя до конца = отказ). Клик по этапу — фильтр `ui.crmStage` в `baseOk`. Новые типы — через `KINDS`, `normKind`, `KIND_ICO`, `ensureKindTemplate`.
- Инфобизнес (`isInfo()`, `kind:'info'`): одна общая доска вместо списка проектов. При открытии пространства без проектов `ensureInfoBoard()` (в `render()`, только когда облако загружено) создаёт проект-доску с постоянным id `infoboard` по шаблону «Инфобизнес: запуск» (`ensureInfoTemplate`, id `tinfo`: Продукт → Контент → Прогрев → Запуск → Продажи → Сопровождение). Матрица, канбан и архив скрыты (`INFO_HIDDEN`), вместо них сразу «Производство»; «Нового проекта» нет (`openCreate` открывает доску, CSS `body[data-kind="info"]` прячет `#newBtn`, список и выбор проектов). Этапы и подэтапы доски правятся в «Настройки → Шаблоны» и расходятся на доску обычной синхронизацией шаблона. На телефоне нижнее меню — `mnavMain()`. Раздел «Контент» (`ui.view = 'content'`, `renderContent`, виден только в инфобизнесе): видео — это подэтапы этапа «Контент» доски (`contentStage()`, по `tsid` этапа шаблона или по названию), те же данные, что на доске: `x.due_date` — публикация, `x.cycle` — старт 4-недельного цикла, `x.done` — опубликовано (дата — `x.u`). «Добавить видео» (`addContent`) — N видео поровну на недели цикла; план — недельный KPI: свой на каждую неделю цикла (`p.ctWeeks[старт] = [n1..n4]` у инфоповода) → общий KPI инфоповода (`p.weekKpi`, одинаково на каждую неделю) → старый `db.prefs.infoPlans[старт]` поровну → по числу видео; правится кнопкой «KPI на неделю», факт — отмеченные (`ctStats`). Отметка в «Контенте» = `toggleSub` на доске. В «Контенте» два вида (`ui.ctMode`): «План / Факт» (по умолчанию, первым) и «Доска» (`ui.ctMode = 'board'`) — колонки этапов шаблона «SMM: видео» (`vidCols`, шаблон добавляется в инфобизнес сам, правится в «Настройках»), у видео `x.vst` — id этапа шаблона; перенос (выбор этапа или перетаскивание, `moveVideo`) в последнюю колонку «Опубликовано» = отметка видео на основной доске. Тест — `tests/info.test.js`.
- Инфобизнес → «Воронка» над доской (`flowPanelHtml`, в `renderProduction`): этапы доски цепочкой со стрелками и «Срочно». Связи — `p.flow = { этап:[этапы-источники] }` у доски (нет записи — зависит от предыдущего, `flowDeps`), меняются кнопкой «Связи» (`ui.flowEdit`, «Как по порядку колонок» сбрасывает). Состояние (`flowState`) — по задачам этапа: красный — есть просроченные (`t.due_date` или `x.due_date` < сегодня) или нет задач; жёлтый — срок сегодня/завтра или ждёт красный источник (по цепочке, `down`/`blockedBy`); «Срочно» — красные по числу тех, кого тормозят, с просроченными задачами (открываются кликом).
- Инфобизнес → «Таймлайн» (переключатель «Доска / Таймлайн» в блоке «Воронка», `ui.infoMode`, `timelineHtml`): строка на этап, задача — точка в день срока (дорожки внутри строки, чтобы подписи не налезали), выходные затенены, линия «сегодня»; стрелки — связи `p.flow` от последнего срока источника к первой задаче зависимого после него (красные — от просроченного источника). Клик по задаче открывает карточку. Оформление воронки — плашки статусов приложения (`.pill.st-pill`, `FLOW_PILL`).
- Доска видео в «Контенте» берёт этапы и подэтапы из шаблона SMM-пространства (`syncVidTplFromSmm`: сам, раз за открытие вкладки — кнопки нет; `smmSpace()` — первое пространство типа SMM, шаблон `tsmm` или с «SMM» в названии; id этапов сохраняются). Подэтапы текущего этапа — галочки на карточке видео (`x.vs[id подэтапа]`).
- Колонка «Контент» на доске инфобизнеса: свои задачи (подэтапы без `x.cycle`, добавленные «Добавить подэтап» — встают в начало, `x.at`) показываются сверху, новые первыми, видео — ниже (`boardSubs`, и на телефоне, и на компьютере).
- Инфоповоды («Контент Игоря», «Челлендж Эма»): каждый — своя доска, проект по шаблону `tinfo` (`infoBoards()`, по дате старта). Строка инфоповодов над воронкой в «Производстве» (и в «Контенте», если их больше одного) — `infoTabsHtml`: переключение (`ui.prodProject`), «+ Инфоповод» (`createInfoBoard`: колонки и связи `p.flow` — как у текущего, задачи пустые, старт — после финиша текущего), карандаш — карточка проекта (название, даты, архив). `infoBoard()` — выбранный инфоповод; «Контент», воронка и таймлайн — его.

Ежеминутная перерисовка пропускается, пока фокус в поле на странице. Задачи инфобизнеса, переименованные до исправления, чинятся при отрисовке (`syncInfoNames`: подэтап берёт `t.title`).

Хранится у инфоповода `p.ai = { at, hash, res }`; статусы отделов на карточках и вывод в шапке — из разбора. Запускается сам при открытии доски, если данные поменялись (`flowAiHash`) и прошлому разбору больше 10 минут (`maybeFlowAi`), и кнопкой «Обновить разбор». Без входа/AI — запасной вывод по срокам (`.fl-why-box`: «Воронка не работает, потому что…», цепочка `chain`). «Срочно сделать» — просроченные задачи, «Горит», «После дедлайна». Хелперы: `areaList`, `spArea`, `curArea`, `spacesOfArea`, `createArea`, `openArea` (последнее открытое — `localStorage kz-area-last-<a>`, пустая область — форма первого пространства `#spFirst`).
- После входа руководителя (раз за вкладку, `sessionStorage kz-picked`) — экран «Где работаем?» (`maybePick`/`paintPick`): области и «+ Новая область». В левой панели — название области со стрелкой ▾ (`areaBar`, выпадающий список областей и команд руководителя, «+ Новая область») и кружки всех пространств области (`sideSpaces`).
